# 예약 동시성: 격리 수준 × 락 전략 비교 (14주차, `chore/concurrency-lock-experiment`)

도전 과제 ① "예약 동시성"(`docs/architecture.md` §8-1, `docs/domains/rental.md` REQ-013 "원자적 처리")의 비교 실험이다. 1순위 완료 판정 "동시 예약 중복 0건"(`docs/roadmap.md` "1순위 착수 순서" 8번)의 근거다. 연장(REQ-038) 경로, 장애 주입(§8-2), 운영 환경 측정은 범위 밖이다.

- **기본 전략은 바꾸지 않았다.** P1이 지연·처리량에서 R보다 낫게 나왔지만, 이 측정은 단일 MySQL·같은 PC이고 커넥션 점유 영향(풀 10개 × 앱 2개)을 따로 재지 않았다. 사용자 결정으로 기본값(R + READ COMMITTED)을 유지하고, P1은 후보로 남긴다. P1을 다시 검토하려면 인기 물품 경합과 다른 API를 섞은 부하로 커넥션 풀 영향을 먼저 재야 한다.
- 1순위 완료 판정: 기본 경로(RC×R)로 C1 60라운드·C2 20라운드·C3 800건·D 약 10.7만 건에서 **중복 예약 0건**, 기타 실패 0건. 측정 끝에 기본 경로로 되돌려 C1을 한 번 더 돌린 것(RC-R-END)도 0건이다.
- 락 대기 초과(`RENTAL_LOCK_TIMEOUT`)는 어느 구성에서도 0건이었다. 한 라운드(100명)는 R·P1 모두 3초(`rental.lock-wait`) 안에 끝났다.

## 비교한 구성

| 이름 | 직렬화 방식 | 충돌 시 응답 |
| --- | --- | --- |
| N0 | 없음(대조군). 겹침 검사 쿼리 + INSERT만 | 검사에 걸리면 409 `RENTAL_PERIOD_CONFLICT` |
| O | 낙관적: 트랜잭션 처음에 `items.version`을 읽고, INSERT 뒤 `UPDATE items SET version = version + 1 WHERE id = ? AND version = ?`. 0행이면 롤백 | 409 `COMMON_CONCURRENT_UPDATE`. 교착(1213)도 충돌로 본다 |
| O2 | O + 충돌 시 재시도 2회(실험 파라미터, 정책값 아님). C3에서만 | 같음 |
| P1 | 비관적: 트랜잭션 첫 문장 `SELECT id FROM items WHERE id = ? FOR UPDATE`. `innodb_lock_wait_timeout` = `rental.lock-wait` 3초 | 대기 초과 409 `RENTAL_LOCK_TIMEOUT` |
| P2 | 비관적: 겹침 검사가 읽는 범위 `SELECT id FROM rentals WHERE item_id = ? AND status IN (활성) FOR UPDATE` | 대기 초과 409 `RENTAL_LOCK_TIMEOUT`, 교착 409 `COMMON_CONCURRENT_UPDATE` |
| R | Redisson `lock:item:{itemId}`, 대기 3초·임대 시간 없음(기본 전략) | 대기 초과 409 `RENTAL_LOCK_TIMEOUT` |
| U | 락 없음. 예약 INSERT 뒤 같은 트랜잭션에서 날짜마다 `rental_dates` INSERT, UK 위반이면 롤백 | 409 `RENTAL_PERIOD_CONFLICT`, 교착 409 `COMMON_CONCURRENT_UPDATE` |
| RU | R 안에서 U | 같음 |

격리 수준 접두사: RC = READ COMMITTED, RR = REPEATABLE READ. 구성 14개(RC×{R, N0, O, P1, P2, U, RU}, RR×{N0, O, P1, P2, R, U, RU}) + O2 2개.

## 해석

1. **락 없이는 격리 수준과 상관없이 중복이 난다.** 겹침 검사(SELECT)와 INSERT 사이에 다른 트랜잭션이 끼어든다. RR의 일반 SELECT는 스냅샷을 읽을 뿐 다른 트랜잭션의 INSERT를 막지 않으므로 RC보다 나을 것이 없다(C1 생성 277~320건). D처럼 경합이 드물어도 RR-N0에서 1쌍이 나왔다.
2. **"읽은 행을 잠그는" 비관적 락(P2)은 행이 없을 때 실패한다.** RC에는 갭 락이 없어 잠글 활성 대여가 없는 기간이면 아무것도 막지 못한다(C1 중복). RR에서는 다음 키 락(갭 포함)이 INSERT를 막아 중복은 없지만, 두 트랜잭션이 같은 갭에 락을 쥔 채 서로의 INSERT를 기다려 교착이 난다(C1 438~536건, C2 818건). 겹치지 않는 기간도 같은 갭을 공유해 C3의 정상 요청 800건 중 705건이 교착으로 거절됐다.
3. **물품 행 잠금(P1)은 정확하고 빠르다.** 행이 늘 있는 물품을 잠그므로 격리 수준과 상관없이 직렬화되고, RR에서도 락을 먼저 잡은 뒤 스냅샷이 만들어져 앞 커밋을 본다. 같은 물품 100명이 한 줄로 서도 Redis 왕복이 없어 R보다 C1 p95가 약 40% 짧다(181~198 vs 307~330ms). 다만 이번 측정에 없는 위험이 있다: 기다리는 요청이 **DB 커넥션을 쥔 채** 최대 3초 기다리므로, 인기 물품에 몰리면 Hikari 풀(앱당 10개)을 다른 API까지 쓰지 못하게 된다. R은 커넥션을 잡기 전(Redis)에서 기다린다. C1에서 문제가 없었던 것은 한 라운드가 3초보다 훨씬 빨리 끝났기 때문이다.
4. **낙관적 락(O)은 "같은 물품의 다른 기간"까지 충돌로 본다.** version이 물품 단위라 C3에서 정상 요청의 92%가 거절됐다. 또 rentals INSERT의 FK 검사가 물품 행에 공유 락을 걸어, 동시에 version UPDATE(배타 락)를 하려는 트랜잭션끼리 교착이 난다. 그래서 충돌 대부분이 version 불일치가 아니라 교착으로 나타나고, 재시도(O2)는 교착을 더 늘려(1,906건) 지연만 길어졌다(p95 494ms). 예약처럼 충돌이 잦은 쓰기에는 맞지 않는다.
5. **UK(U)는 DB가 최종 방어선이 되지만 교착을 만든다.** 중복은 어느 격리에서도 0이었다. 그러나 날짜 행 여러 개를 INSERT하므로 부분 겹침(C2)에서 순서가 엇갈려 교착이 나고(RC 68·RR 133), RR에서는 중복 키 검사의 다음 키 락 때문에 같은 기간(C1)에서도 188~208건이 교착으로 끝났다. 교착도 409로 돌려주므로 정합성 문제는 아니지만 사용자에게는 "기간 충돌" 대신 "다시 시도" 안내가 나간다.
6. **R(기본)과 RU는 교착 없이 정확하다.** 락이 Redis에서 직렬화하므로 DB 안에서 락끼리 부딪칠 일이 없다. RU는 R에 UK를 더해도 교착이 0이었고(락이 먼저 줄을 세운다) 지연도 같았다. 이번 실험 범위(Redis 정상)에서는 R만으로 중복이 0이라 UK 2차 방어의 이득은 보이지 않는다. 이득은 Redis 장애·락 유실 상황(§8-2 장애 주입, 범위 밖)에서 확인할 수 있다.
7. 격리 수준 RR은 어느 전략에서도 정확도 이득이 없었고, P2·U·O에서는 교착을 늘렸다. 기본값 READ COMMITTED를 유지할 근거다.

## 한계

- 같은 PC에서 MySQL·Redis·앱·k6가 돌았다. Redis 왕복·네트워크 지연이 운영(EC2 2대 + RDS)보다 짧아 R의 상대적 비용은 실제보다 작게, P1의 커넥션 점유 비용은 드러나지 않게 나왔을 수 있다.
- C2·C3·D는 1회씩 잰 값이다. C1의 2·3회차 p95 차이는 락으로 줄을 세우는 구성(R·RU·P1)은 10% 안이었고, 락이 없는 구성(N0·U·O)은 p95가 100ms 안팎이라 최대 약 45% 흔들렸다.
- C3는 40명(오늘+200일부터 시드 예약과 겹치지 않게)이고, 락 대기 초과가 나올 만큼 긴 줄(3초 이상)은 만들지 않았다.
- 실험 전략을 켜면 같은 인터페이스를 쓰는 가능 기간 수정(REQ-007)·연장(REQ-038)도 그 전략을 타지만 측정하지 않았다. rental_dates는 예약에서만 쓴다(취소·만료 시 삭제는 구현하지 않음 — 실험은 매번 초기화한다).
